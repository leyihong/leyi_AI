# Feishu × CALL-E 群聊外呼助手：项目说明

运营在飞书群里发布外呼目的和表格链接，确认任务方案与具体名单后，机器人逐人调用 CALL-E，显示进度，并把结构化结果回填原记录。

## 1. 产品理解与机会判断

CALL-E 提供认证/API、电话执行和目标驱动对话；社区集成负责把这些能力放进具体工作流，处理业务意图、权限、确认、持久化和结果去向。本项目不实现电话 Provider、语音引擎或 CALL-E 内部规划器。

本次选择的机会是：名单已经在表格、任务已经在群聊，但一次电话调用与完整业务操作之间仍有空隙。运营还需要确定联系谁、收集什么答案、怎样避免重复联系，以及把结果准确放回哪条记录。

核心假设是：减少名单搬运和答案转录，同时让操作人员在拨号前核对范围，能降低流程成本和误操作。飞书是验证这个假设的宿主；可迁移的贡献是“经确认的目标、名单快照和原记录结果”之间的关联。仓库缺少飞书示例不能单独证明市场需求，当前也没有用户研究或提效数据足以证明这一假设。

## 2. 目标用户与示例场景

目标用户是使用飞书群和多维表格维护联系人、需要对一批已授权对象收集信息的运营人员；应用配置由具备权限的工作流搭建者完成。

演示场景为活动报名后的参会确认：从视图中选择出席意向仍为待定、允许电话联系的报名者，询问是否能参加，以及是否需要工作人员后续联系。供应商进度、售后反馈可使用不同目的和结果字段，但本期不承诺任意场景都能准确理解。

电话的价值来自对话获取尚未确定的信息。单纯提醒已有截止时间，或让 AI 替业务人员作审批、付款、购买决定，不是本次贡献的目标。

## 3. 用户主流程

1. 在授权群内 @机器人，发送目的、已绑定表格链接、筛选条件及可选结果要求；先收到简短回执。
2. 机器人整理任务方案，展示目的、条件、去重规则、结果字段/枚举和输出列变更。
3. **第一次确认：确认任务定义。** 缺失输出列若已明确批准，则创建并核对；此时不拨号。
4. 读取已绑定视图、筛选并检查授权与号码，按明确规则去重，发送完整名单的分页预览。
5. **第二次确认：确认名单与执行。** 核对模拟/真实模式、实际对象、背景与回填范围，再启动本轮任务。
6. 每人本轮只拨一次；后台有限查询首次结果，群内更新进度。
7. 校验结果并回填原记录，发送终态通知，区分电话情况、业务枚举和回填情况。

可以直接在群内继续修改：`对象：姓名或记录编号`、`目的：新目的`、`筛选：新条件`、`结果：字段=选项/选项`。修改产生新版本并使旧卡失效；已经开始执行的任务不能通过聊天改写。

## 4. 已实现与本期边界

| 领域 | 已实现 | 本期边界 |
| --- | --- | --- |
| 飞书入口 | 授权群/操作者检查、即时回执、长连接消息和卡片事件 | 需自行配置企业自建应用与资源权限；未验证 Lark 租户 |
| 任务理解 | 可选本地 Qwen 受限提案、澄清、多轮修改、差异与私有复核记录 | 规则模式使用明确格式；不保证任意自然语言或复杂业务逻辑 |
| 名单 | 绑定视图、完整分页、AND 筛选、授权检查、同号保留一条、单人精确收窄 | 来源列依赖约定名称；不支持任意列交互映射或复杂 OR/范围计算 |
| 输出字段 | 复用兼容列；缺失文本/单选列先确认再创建 | 不自动改已有列类型或补已有单选选项；最多 5 个业务结果字段 |
| 外呼执行 | Calls v2、单机持久队列、顺序执行、冻结名单、逐人提交前复查 | 无并发外呼、周期调度或任意联系窗口配置；无生产部署保证 |
| 重复与故障 | 持久化请求/幂等键、未知提交停止、结果查询到限停止 | 没有完整提交未知自助恢复后台；不自动重拨 |
| 任务控制 | 暂停/继续/取消剩余；明确失败单人任务可另行确认再拨一通 | 取消不保证挂断已提交电话；停止的结果查询不能用继续恢复 |
| 结果与通知 | 原记录回填、冲突检测、回填独立重试、进度与完成卡、枚举汇总 | 不是跨系统事务；没有历史分析平台或便捷历史搜索界面 |

不设固定业务人数上限，但实际完成规模受单机容量、顺序拨打、额度、联系时间及批次创建窗口限制。不得把“无人数硬上限”理解为可无限时、无限规模执行。

## 5. 关键取舍与责任边界

保留两次确认，因为“方案正确”和“实际名单、模式与写入范围正确”是两个不同判断。模型只能提案，不能授权拨号；它不接收整表通讯录，也不能直接调用电话或表格工具。CALL-E 根据已批准目标、必要背景和结果 schema 进行实际沟通，社区 Skill 不会被 Calls v2 自动调用。

每人每轮一次，首次结果默认最多等待 300 秒或读取 20 次，到限停止，不自动恢复或重拨。电话未接通、线路失败与业务否定分开记录，缺失答案不补猜；机器人接听成功也不等于确认真人参会。

电话会打扰联系人并产生费用。真实模式还须号码白名单、明确授权数据、地区/语言/时区和名单卡批准；提交前重新核对授权、禁止联系、关键来源与本地拒绝联系标记。真人电话限联系人当地 08:00–21:00；固定自动测试热线例外须显式配置并在名单卡披露。

未知提交保留原请求与幂等键，不能换键重拨。回填和通知重试独立于拨号。写入前比较目标值，但这不是原子并发保护，应使用集成专用输出列。群里展示脱敏名单与汇总，个人业务摘要留在原表；凭证、真实联系人、数据库、完整转录和模型权重不进入公开提交包。

## 7. 本地复现与交付形式

这是需要自行配置的可运行集成示例。下载源码后可安装依赖并运行离线测试；完整群聊能力需要自己的飞书应用、测试群和表格权限。自由自然语言功能需另装 Ollama/Qwen；真实电话需自己的 CALL-E 项目 API Key、额度与相应线路访问资格。

源码包不包含作者的凭证、私有数据库、模型权重或已配置企业机器人。运行时只需 Python；通过 Calls v2 调用电话，不要求安装 CALL-E Node.js CLI。安装与配置步骤全部集中在[技术方案第四节](docs/ARCHITECTURE.zh-CN.md#四本地部署与配置)。

评审包包含代码、测试、配置模板和这两份说明；也提供针对空仓库的独立代码补丁，以及安装用 wheel。源码包用于完整评审，wheel 仅用于安装 Python 程序。


## 8. 下一步与 AI 使用说明

优先完成真实运营试用，再按错误频率决定增加来源列映射、提交未知核对入口和历史定位；有需求证据后再考虑调度或其他宿主。缺列确认创建已实现，不再列入未来计划。

AI 辅助仓库研究、方案形成、实现、回归设计和文档整理；人工保留场景选择、范围取舍、字段/名单审阅、真实电话授权及价值判断。提交者应理解两阶段确认、幂等与未知提交的差异，能解释真实、模拟和用户反馈三类证据。
